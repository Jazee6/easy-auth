## Manual Account Security acceptance

Complete and record these checks before presenting 0.5.0 outside local development:

### Account Panel and Two-Factor Authentication management

- [ ] A Standard Account reaches Account Security from the Account navigation after Sign-in methods and before Authorized applications; the Admin navigation group remains unchanged.
- [ ] An Administrator reaches the same Account Security destination and can manage only their own Two-Factor Authentication and Sessions through that destination.
- [ ] A password Account sees Disabled with the explicit local-password boundary and can open the three-stage enrollment flow.
- [ ] A GitHub-only Account sees Disabled, is told that Two-Factor Authentication protects local password sign-in only, and has a direct Set password path; enrollment is unavailable until a local password exists.
- [ ] A linked password/GitHub Account sees the same local-password boundary, while GitHub sign-in remains protected by GitHub and does not enter the Easy Auth challenge.
- [ ] The Disabled and Enabled Cards accurately reflect authoritative state after refresh, navigation, and a second browser.
- [ ] Enrollment requires the current password; incorrect, missing, and stale submission errors are safe and clear on field change.
- [ ] Enrollment renders a locally generated QR code and a copyable manual setup key; scanning does not use an external QR service, `dangerouslySetInnerHTML`, a URL, or persistent browser storage.
- [ ] Setup material remains ephemeral, cancellation before first verification leaves local password sign-in unchanged, and restarting replaces unfinished setup safely.
- [ ] The first valid TOTP completes enrollment; an invalid TOTP does not enable the Account or create an unexpected Session.
- [ ] Backup Codes appear once only after successful enrollment; Copy all, Download, explicit saved-codes acknowledgment, focus management, and keyboard operation work.
- [ ] Dismissing unsaved Backup Codes opens the impact confirmation and preserves the dialog content until the close animation completes.
- [ ] Regeneration requires an impact confirmation and current password, invalidates the complete old set immediately, and uses the same one-time save flow.
- [ ] Existing Backup Codes cannot be viewed or redisplayed by any Account-panel action.
- [ ] Disablement requires a fresh Session and current password, does not require a TOTP, removes the Two-Factor record, and presents its destructive impact clearly.
- [ ] Successful enablement and disablement preserve the current Session, terminate all other Easy Auth Sessions, preserve OAuth tokens and Application Authorizations, and leave a visible retry warning if post-change cleanup fails.
- [ ] Successful disablement removes every Trusted Device record and the current browser's trust cookie; ordinary Session termination does not claim to untrust a browser.
- [ ] Password Reset preserves Two-Factor Authentication while retaining its existing all-Session revocation behavior.
- [ ] No Two-Factor or Session email notifications, new self-service Security activity history, Administrator reset control, or Trusted Device list appears.

### Password login challenge

- [ ] A Two-Factor-enabled Account that signs in with a local password receives the public challenge route after password verification, with no authenticated Session while the challenge is pending.
- [ ] TOTP is the primary accessible fixed-length Input OTP form; keyboard input, paste, and password-manager workflows work.
- [ ] Backup Code is an explicit alternate form and each code succeeds only once; replay is rejected without exposing internal details.
- [ ] Trust this device is a shadcn Checkbox, starts unchecked, and when selected follows Better Auth's rolling 30-day Trusted Device lifetime.
- [ ] A valid Trusted Device skips the second factor on local-password login, and terminating its resulting Session leaves trust unchanged.
- [ ] Invalid code, consumed Backup Code, missing/malformed cookie, expired challenge, exhausted challenge, endpoint throttling, temporary account lock, and lock expiry each have concise safe feedback and restart behavior.
- [ ] Restart login returns to password entry while preserving a valid signed OAuth/OIDC continuation; no challenge cookie, continuation, password, TOTP secret, Backup Code, or Session token appears in an unintended URL, loader, response, log, or rendered output.
- [ ] Successful ordinary login reaches the normal Account destination and creates exactly one Session.
- [ ] Successful OAuth/OIDC login reaches the existing authorization/consent path only after TOTP or Backup Code verification.
- [ ] GitHub sign-in bypasses the Easy Auth Two-Factor challenge and the explanatory copy does not imply Account-wide or GitHub Two-Factor protection.

### Safe Account Session management

- [ ] Security lists every active Session without pagination, omits expired rows, marks the current Session first, and orders other Sessions by update time descending with Session-ID tie-breaking.
- [ ] Every Session shows browser, operating system, device type, IP address, creation, update, and expiry times; missing or unrecognized metadata displays as Unknown.
- [ ] Session credentials, impersonation values, and bearer tokens are absent from route data, network responses, URLs, logs, errors, and rendered output.
- [ ] Any valid current Session can inspect only its own safe Session projection; anonymous access and cross-Account Session IDs are rejected.
- [ ] A stale Session can inspect the list but cannot revoke another Session or all other Sessions; the UI gives a clear sign-in-again path.
- [ ] Remote single-Session revocation validates ownership and active state, requires Better Auth's default fresh-Session window, confirms impact, refreshes authoritative state, and handles simultaneous/stale/missing IDs safely.
- [ ] Revoke all other Sessions confirms impact, preserves the current Session, refreshes the list, and does not revoke Trusted Devices, OAuth tokens, or Application Authorizations.
- [ ] Terminating the current Session uses the existing Sign out behavior rather than a second remote-revocation flow.
- [ ] The Empty component explains the no-other-active-Sessions state, and all pending buttons are disabled with Spinner placement before text.
- [ ] Administrator self-service works for their own Sessions without changing the prohibition on Administrator actions against another Administrator; Admin actions against Standard Accounts retain existing Security activity behavior.

## Residual risk

Easy Auth remains development-stage. This release does not claim production readiness, compliance certification, high availability, monitoring, deployment automation, or durable atomic audit guarantees. There is no browser E2E framework and no notification email for Two-Factor or Session actions. Account/Admin self-service factor-loss recovery is intentionally absent; factor loss requires the operations-only, out-of-band-verified recovery wizard. Already delivered ID tokens, stateless artifacts, and relying-party local Sessions cannot be recalled by Easy Auth.

ShellCheck was unavailable in this qualification environment and therefore was not run. Remote D1 Time Travel, Wrangler authentication, real Authenticator App scanning, external OAuth/GitHub/Turnstile/Resend behavior, browser network inspection, keyboard/mobile interaction, and all other browser-dependent checks remain pending until manual acceptance. Cloudflare Workers Free Tier Time Travel retention is seven days; this is a recovery point, not indefinite disaster recovery.

No unselected OTP, passkey, WebAuthn, product Trusted Device management, Session history/pagination, Account self-service Security activity, Administrator reset, or OAuth ownership capability was added by 0.5.0 qualification.
